# RedeemPool

The RedeemPool is the core mechanism through which VT holders receive underlying tokens (T) during the vesting period. Users stake VT in the pool; the pool automatically pulls T from the vault per the DFIOracle schedule, burns VT 1:1 as T arrives, and distributes T to stakers proportionally — minus a protocol fee (e.g., 5%).

## How It Works

```
User stakes VT → receives shares
                      ↓
   Pool pulls T from Vault per DFIOracle schedule
                      ↓
   For every T pulled: 1 VT is burned 1:1
                      ↓
   Stakers accumulate claimable T
   (pro-rata by shares, minus e.g., 5% protocol fee)
                      ↓
   User calls claimT() → receives their T
```

The RedeemPool does not hold a pre-funded reserve of T. Liquidity grows gradually as the DFIOracle schedule releases tokens from the vault.

## Numeric Example

From the contract (5% fee, protocolFeeRate = 50):

```
TotalStakedVT = 50, user holds 5 VT → 5 shares

Vault releases 10 T → Pool pulls 10 T
→ Burns 10 VT (pool shrinks: 40 VT remaining, 50 shares)
→ Share value drops: 40/50 = 0.8 VT per share

User's claimable T += 10 × (5/50) × 0.95 = 0.95 T
                        (proportional) (after fee)
```

The 5% fee (e.g., 0.05 T here) accrues to the protocol treasury. Users receive 95%.

## User Functions

### Stake VT

```solidity
function stakeVT(uint256 amount) external;
```

Deposits `amount` VT into the pool. Shares are issued at the current share-to-VT ratio. A lazy pull from the vault is triggered first to ensure staking starts with up-to-date rewards accounted for.

### Unstake VT

```solidity
function unstakeVT(uint256 shares) external;
```

Returns the VT equivalent of `shares` to the caller. Note: the parameter is **shares**, not VT amount — share value declines over time as VT is burned during pulls.

### Claim T

```solidity
function claimT() external;
```

Triggers a vault pull first, then transfers all accumulated claimable T to the caller. The fee (e.g., 5%) has already been deducted from the accumulated amount at distribution time.

## Lazy Pull Mechanism

The RedeemPool does not run on a cron schedule. Instead, `_tryPullFromVault` is triggered automatically whenever a user calls `stakeVT`, `unstakeVT`, or `claimT`. This pull queries the DFIOracle for how much T is currently releasable, pulls that amount from the vault, burns the corresponding VT, and updates staker balances.

This design means:
- No keeper or bot is required
- Gas costs are distributed across user interactions
- The pool always syncs to the latest oracle state before any state change

## Price Floor Effect

Because staking in the RedeemPool guarantees receiving (1 − fee) of the underlying over time, it creates a soft floor for VT market prices. VTs trading below `(1 − fee)` on an AMM represent an arbitrage: a buyer could purchase cheap VTs and stake them to recover, e.g., 95% of par.

```
Soft price floor ≈ (1 − protocolFeeRate / 1000)
e.g., 0.95 underlying per VT  (at 5% fee)
```

## Dust Protection

The pool enforces a minimum residual VT (`dustProtection`, default 1e18) that cannot be burned. This prevents the pool from reaching a degenerate state with zero VT. Any T that arrives when no further VT can be burned accumulates as `excessT` and becomes available for Maturity `redeemVT()`.

## Maturity: redeemVT

After the vesting schedule ends, `vestingEnded` is set to `true` and staking is disabled. VT holders can then call:

```solidity
function redeemVT(uint256 vtAmount) external;
```

This burns VT 1:1 from the `excessT` reserve. No protocol fee applies to Maturity redemption.

<Callout type="info">
Maturity redemption via `redeemVT()` is always 1:1 and fee-free. It covers VT that was never staked, or residual VT left after all vesting period pulls.
</Callout>

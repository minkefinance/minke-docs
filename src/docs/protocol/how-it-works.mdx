# How It Works

Minke converts illiquid future-income positions into tradable tokens. No oracles. No counterparty. No haircuts.

## Two Pool Modes

Minke supports two pool modes. Both follow the same creation path — **Create Oracle → Create Vault** — with the mode selected when you configure the oracle. The difference is in how VT reaches investors.

| Mode | Who mints VT | Oracle type | Best for |
|---|---|---|---|
| **Standard Pool** | Issuer mints VT directly to each investor | PIECEWISE release schedule | Token vesting, airdrops, lock-up programs |
| **Custom Pool** | Investors deposit an asset to receive VT at a declining rate | CURVE (rate decay) | Farming, DePIN rewards, loyalty programs |

Both modes share the same VT Token, RedeemPool, and Maturity redemption mechanics.

---

## Creation Flow (both modes)

```
1. CREATE ORACLE  — Issuer configures a DFI Oracle (schedule or rate curve), deploys on-chain
2. GET APPROVED   — Minke team reviews oracle via GitHub Issue
3. CREATE VAULT   — Issuer selects the approved oracle and deploys the vault
4. FUND           — Issuer deposits DFI tokens (T) into the vault
5. APPROVE POOL   — Issuer grants Redeem Pool permission to pull T
```

After setup, the two modes diverge in how VT is distributed:

| Mode | Step 6 |
|---|---|
| **Standard Pool** | Issuer calls `mintVT(to, amount)` for each investor |
| **Custom Pool** | Investors call `deposit(amount)` → receive VT at the current oracle rate |

## Investor Journey (both modes)

Once VT is in investor wallets, the experience is identical across both modes:

### Option A — Stake in RedeemPool

```solidity
function stakeVT(uint256 amount) external;
function claimT() external;
function unstakeVT(uint256 shares) external;
```

The RedeemPool lazily pulls T from the vault per the DFIOracle schedule, burns VT 1:1 as T arrives, and distributes T proportionally — minus the protocol fee (5%). Investors call `claimT()` to receive their accumulated T.

### Option B — Trade on AMM

VTs are standard ERC-20 tokens. Holders can sell on any DEX at a market discount. Secondary buyers make a time-value bet: they acquire future claims cheaply and either stake for gradual T or redeem at par at maturity.

### Option C — Wait for Maturity

Once the vesting schedule ends, `vestingEnded` is set on the RedeemPool. Any VT holder can call:

```solidity
function redeemVT(uint256 vtAmount) external;
```

Burns `vtAmount` VT 1:1 from the pool's `excessT` reserve and transfers T to the caller. No protocol fee.

```
redeemed = 1 underlying per VT  (always exactly 1:1)
```

## Shared Mechanics

| Concept | Detail |
|---|---|
| **VT** | ERC-20, transferable, tradable on any DEX |
| **DFI Oracle** | Stores the release schedule or rate curve on-chain as an EIP-1167 clone |
| **RedeemPool** | Lazy pull from vault per DFIOracle; proportional T distribution |
| **Protocol fee** | Fixed 5% deducted from vesting distributions only |
| **Maturity** | `redeemVT(vtAmount)` — 1:1 T from `excessT` reserve, no fee |

<Callout type="tip" title="No oracles, no liquidations">
The DFI Oracle stores the vesting schedule or rate curve on-chain — no external price feed is ever consulted. The 1:1 backing guarantee is mathematical, making the system immune to oracle manipulation and collateral cascades.
</Callout>
